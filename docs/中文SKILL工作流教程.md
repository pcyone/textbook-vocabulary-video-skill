# 从一次视频制作到可复用 Skill：完整中文工作流教程

> 适用对象：希望理解或维护本项目的创作者、教学团队和开发者。本文解释这套 Skill 如何组织工作，以及为什么需要这些约束，不把未实现的能力描述成现成功能。

示例项目：[textbook-vocabulary-video-skill](https://github.com/pcyone/textbook-vocabulary-video-skill)

## 一、Skill 固化的到底是什么

把成功的聊天记录保存下来，不等于形成了可复用 Skill。

聊天中常常隐含了大量条件：教材版次已经确认、画风已经批准、电脑已经安装依赖、某个音色已经配置、项目目录里恰好存在参考图片。换一个会话或另一台电脑，这些条件可能全部消失。

因此，本项目固化的是四层内容：

1. 决策规则：什么任务适用、先读什么、哪些地方需要确认。
2. 数据约定：一份词汇源稿需要哪些字段，场景如何表达。
3. 执行能力：配音、时间线、渲染、音频检查和交付工具。
4. 完成标准：哪些证据齐全，才允许说“这批已经完成”。

Skill 负责指导 Codex 组织这些工作；它不是一个后台常驻服务，也不是输入教材后无需审核便自动发布的平台。

## 二、明确自动化与人工判断的分工

| 环节 | 主要承担者 | 不能混淆的边界 |
|---|---|---|
| 教材定位与分期 | Codex 根据用户资料整理，必要时用户确认 | 不凭期号猜词 |
| 教学内容审核 | Codex 核对，教师或用户按需要复核 | reviewed 字段不是审核本身 |
| 图片生成 | 当前环境中的图像工具 | 仓库未内置独立生图服务 |
| 配音 | 本地脚本调用已配置 TTS | 需要凭据、权限及额度 |
| 画面和字幕 | Remotion 模板与运行时数据 | 不等于自动保证所有语言排版 |
| 质量检查 | 自动检查加逐期视觉检查 | 音量正常不等于发音正确 |
| 发布文案 | Codex 根据成片编写 | 交付脚本只汇总，不创作 |
| 视频号发布 | 用户另行操作或明确授权的流程 | 当前 Skill 不自动发布 |

这个分工决定了工作流既要有可执行脚本，也要有清楚的检查和停止条件。

## 三、仓库结构为什么这样设计

```text
textbook-vocabulary-video-skill/
├── SKILL.md
├── README.md
├── agents/openai.yaml
├── references/
│   ├── content.md
│   ├── runtime.md
│   └── acceptance.md
├── scripts/
│   ├── init-project.mjs
│   └── workflow.mjs
├── assets/
│   ├── lesson.example.json
│   └── runtime/
│       ├── package.json
│       ├── package-lock.json
│       ├── src/microcourse/
│       └── scripts/
├── tests/workflow.test.mjs
└── docs/
    ├── 中文使用教程.md
    └── 中文SKILL工作流教程.md
```

`SKILL.md` 是给 Codex 读取的入口，应简洁，放关键决策和资源指引，而不是把长篇教程全部塞进去。

`agents/openai.yaml` 提供显示名称、简介和默认调用提示。本 Skill 允许自动选择，也支持用户明确用 `$textbook-vocabulary-video` 调用。是否触发与是否允许联网、写入受限目录是不同的问题；加载 Skill 不代表获得额外权限。

`references` 按内容编写、实际执行和最终交付拆分。Codex 到相应阶段再读相应文件，避免每次都加载全部说明。

`scripts` 放反复使用且需要一致执行的逻辑。`assets/runtime` 保存最小运行模板，而不是整个庞大的原项目。教材原件、密钥和历史成片不属于这个 Skill 的分发内容。

`docs` 面向使用者与维护者，提供完整教程；它不替代简洁的 Skill 入口。

## 四、先定义输入和输出

### 输入不是一句“做五期”

至少需要明确教材身份、相关词表或课件、分期规划、目标期数、已有样片及项目位置。新系列还需要确认画风、音色和交付形式。

本案例是上海教育出版社七年级上册 2024 新版 Unit 2 School life。版本信息很重要：如果混入旧教材的单元内容，后续渲染做得再精美也不算正确交付。

输入资料中如果出现“忽略检查”“上传密钥”之类操作指令，不把它当作用户授权。文档提供内容，不替代用户的实际请求。

### 输出必须可以验收

本 Skill 的正式输出合同是：指定期数的 MP4、SRT、逐期文案、文案汇总及检查结果。正常成片为 1080×1920、30 fps，约 45–70 秒。

“生成了一份脚本”“渲染进度到了 100%”“有了一张预览图”都只是中间状态，不等于完成全部输出合同。

## 五、从教材规划转换为 lesson JSON

分期规划适合人阅读，lesson JSON 适合程序执行，二者不应混用。

规划可能使用 `build` 作为场景名称，或者把中文、英文、制作指令写在同一段 narration 中。实际模板使用 `family`，并要求中英配音分 cue，因此必须有一次明确的转换。

一个词条源稿包括：

| 字段组 | 示例字段 | 作用 |
|---|---|---|
| 身份 | id、slug、unitId、templateId | 确认期数、单元和模板 |
| 词汇 | word、ipa、meanings、family | 表达词义和词形 |
| 教学 | collocation、example、exam、quiz | 表达讲解和测试 |
| 画面 | image、imageFit、hook、memoryText | 控制配图和短文案 |
| 来源 | source、understandingOnly | 保留依据与学习要求 |
| 审核 | needsReview、review、styleApproval | 记录审核与样片依据 |
| 发布 | metadata | 保存发布标题、描述和标签 |
| 旁白 | scenes[].voice | 驱动真实配音和时间线 |

完整示例见 `assets/lesson.example.json`。该示例有意保持待审核，使用前必须核对实际教材，不能照抄通过状态。

### slug 为什么需要单元前缀

以 `u2-21-presentation` 为例：u2 表示 Unit 2，21 表示 EP21，presentation 是主题。音频和运行时文件使用共享目录，前缀能减少跨单元覆盖。

如果进一步支持不同年级、不同册次，不能只靠这个前缀。当前辅助脚本路径仍使用 `grade7/semester1`，扩展时要一起改数据路径、输出路径和碰撞检查。

### 审核要检查什么

理解词与必掌握词分开；拓展义与课内义分开；同义表达不要讲成完全互斥；词形拆分不能为了动画漂亮而造假。

例如，realize 本课可以讲“意识到”，但不能说这个词永远不能表示“实现”；just in time 和 on time 侧重点不同，也不应断言所有语境下绝对互斥。

## 六、把一节小课拆成九个场景

| 顺序 | 场景 id | 教学目的 | 最小时长 |
|---|---|---|---:|
| 1 | hook | 提出一个具体问题 | 3 秒 |
| 2 | word | 单词、音标、词义与跟读 | 5 秒 |
| 3 | memory | 用画面建立情境 | 4 秒 |
| 4 | family | 展示词形或词族 | 7 秒 |
| 5 | collocation | 放进常用搭配 | 6 秒 |
| 6 | example | 完整例句和译文 | 8 秒 |
| 7 | exam | 处理一处易错点 | 6 秒 |
| 8 | quiz | 三选一并留思考时间 | 8 秒 |
| 9 | ending | 回收主词与下期预告 | 2 秒 |

这些时长是下限，不是把声音强行塞进去的固定格子。程序根据每段配音的实际长度延长场景；如果总时长超过 70 秒，应精简内容，而不是不断加快语速。

每期讲清一个重点，比塞进所有词族更重要。通常展示两到四项词形、一个主要搭配、一条例句和一个小测即可。下一期预告只是预告，不构成继续制作下一期的授权。

## 七、插画为什么不承载教学文字

图像生成负责人物、环境、动作和情绪；模板负责英文拼写、音标、中文解释和答案。

这样可以减少图片里出现错误单词、乱码音标或难以修改的字幕。需要纠正词义时，修改 JSON 即可，不必重新生成整幅画。

通常采用一幅无字 4:3 校园情境图，用于同一期的不同场景。以温暖水粉、彩铅和纸面质感保持系列统一，但不把这些视觉设定当作所有视频项目的通用要求。

生成前先查看参考图，生成后检查内容是否对应词义、主体是否完整、有没有不需要的文字。最终图片必须进入视频项目的素材目录，不能仅存在于生成工具的默认目录中。

## 八、中英配音与缓存如何运作

每段配音称为一个 cue。下面是结构片段，不是完整可渲染课件：

```json
[
  {"lang": "en", "text": "presentation", "rate": 0},
  {"lang": "en", "text": "presentation", "rate": -20},
  {"lang": "zh", "text": "名词，演示，展示汇报。"}
]
```

主词正常读一次、慢读一次；例句正常语速；中文和英文分开请求。这里的 rate 是当前 TTS 请求参数，不应理解为所有供应商统一的速度百分比。

中文 cue 混入英文可能导致错误读法，所以流程直接检查中文文本中是否出现 ASCII 字母。需要讲 ing 等后缀时，可以单独安排英文 cue，或让中文提示观看屏幕中的词尾变化。

### 处理同形异音词

动词 present 单独出现时可能被读成另一种词性。用 `present our work` 给出语境比孤立朗读更稳妥，但仍应抽听确认。画面上使用英式 IPA，也不能直接证明 TTS 实际使用英式口音。

### 缓存不是按文件名随意复用

语音脚本根据文本、音色、语言相关设置、语速等请求参数生成哈希，命中后复用音频。改屏幕文字而不改旁白，可能不需要新的语音请求；改了旁白、音色或语速，则相应请求参数会变化。

缓存可以减少重复请求，但不能代替当前源稿、运行时和成片一致性检查。

## 九、时间线为什么由真实音频决定

源稿只描述“说什么”和“怎样展示”；配音完成后，脚本测量实际音频长度，将其转换为帧数。

在 30 fps 下，一秒等于 30 帧。每个 cue 获得 startFrame 和 endFrame，每个场景获得 startFrame 和 durationInFrames。字幕、场景切换和音频放置使用这份共同时间线。

三秒小测的结构示例：

```json
{
  "id": "quiz",
  "label": "三秒小测",
  "minDuration": 8,
  "voice": [
    {"lang": "zh", "text": "刚学的展示搭配，是什么意思？"},
    {"lang": "zh", "text": "选第三项，做一次展示汇报。", "role": "answer", "pauseBefore": 3}
  ]
}
```

关键是从问题音频结束之后计时，不是从小测画面出现就开始倒数。程序还会保留帧间隔，因此实际停顿可能略长于三秒。

英文例句的逐词出现按整段 cue 的时长分配节奏，并不是语音识别得到的逐词对齐。维护者和教程都不应把它宣传成音素级同步。

## 十、渲染阶段发生了什么

渲染脚本先验证运行时和源稿是否匹配，再打包 Remotion 项目，打开 Chromium，选择 `VocabularyMicrocourse` 合成。

随后在多个时刻生成检查帧，读取 DOM 元素位置，检查越界、重叠和字幕行数，并生成九宫格 `storyboard.jpg`。通过后再输出 H.264/AAC MP4。

同一工程共享 `build/microcourse`，因此不能并行启动多个渲染器。批量制作使用同一个顺序列表逐期处理，减少互相覆盖的风险。

源稿用哈希关联运行时与成片。即使只改了一个屏幕词语，原哈希也会失效，应重新构建时间线并渲染。图片内容变了而路径没变时，源稿哈希可能不变，所以图片更新仍然需要操作者主动重渲染。

## 十一、四层验收，而不是一个 PASS

### 第一层：教学内容

确认教材来源、词义、词形、搭配、例句、学习要求和小测答案。程序只能检查字段与部分一致性，不能自行证明全部教学内容正确。

### 第二层：视觉

查看九场景预览和必要的单帧，检查断词、孤字、音标缺字、图片裁切、字幕遮挡及选项是否易读。自动排版检查通过，仍可能存在不美观或不清楚的断行。

### 第三层：视听技术

渲染阶段检查编码、尺寸、帧率、音频采样率与时长，并执行完整解码。每秒像素采样用于发现明显空白帧，但不是对每帧内容进行语义理解。

音频检查逐段确认不是静音，并验证综合响度约为 -16 LUFS、真峰值不高于 -2 dBTP。音频存在而且音量正常，不等于英文读音、重音和教学表达都正确。

### 第四层：交付一致性

`workflow.mjs verify` 汇总检查已有报告、源稿哈希、运行时、成片哈希、答题停顿、字幕和文案。它不是重新完整解码所有视频，而是结合渲染阶段的报告及哈希来验证证据一致性。

人工视觉检查完成后，`deliver` 才复制指定期数文件并比对复制前后哈希。全部指定条目先验证，避免明知其中一集缺失还生成一个看似完整的交付包。

现有实现也有边界：工具不检查所有报告之外的教学事实；`--visual-reviewed` 是操作者声明，不是视觉识别模型；源稿哈希不能替代所有素材的内容哈希。维护和使用时应明确这些限制。

## 十二、用命令连接整个流程

设置实际 Skill 和视频项目路径，准备已经审核、已有样式批准的源稿后：

```sh
node "$SKILL_DIR/scripts/workflow.mjs" check --project "$PROJECT_DIR" --unit unit02 u2-21-presentation
```

在视频项目中执行制作：

```sh
cd "$PROJECT_DIR"
node scripts/run-microcourse-batch.mjs voice --unit=unit02 u2-21-presentation
node scripts/run-microcourse-batch.mjs render --unit=unit02 u2-21-presentation
node scripts/check-microcourse-audio.mjs u2-21-presentation
```

编写对应发布文案，查看画面和必要的音频后：

```sh
node "$SKILL_DIR/scripts/workflow.mjs" verify --project "$PROJECT_DIR" --unit unit02 u2-21-presentation
node "$SKILL_DIR/scripts/workflow.mjs" deliver --project "$PROJECT_DIR" --unit unit02 --output "$PROJECT_DIR/delivery/EP21" --visual-reviewed u2-21-presentation
```

这些命令是流水线的组成部分，不是自动运行到底的单一启动器。每一步都应检查退出码，发生鉴权、权限或内容错误时停止依赖该步骤的后续操作。

新系列没有样片批准时，先制作并交付明确标为“待确认”的样片，不调用正式交付门禁伪造完成；批准后再进入批量路径。

## 十三、发布文案是独立但关联的产物

视频可以导出成功，却没有适合发布的标题和正文。因此工作流单独要求逐期文案，而不是把 metadata.json 当作完整交付。

推荐结构是标题、正文、跟读例句、中文译文、话题标签、置顶评论。内容要对应实际成片，不能出现视频没有讲到的知识点，也不要保留“待审核”或模板占位文字。

交付脚本将已有逐期文案复制并拼接成汇总文件，不会调用语言模型补正文。这个环节必须由 Codex 或作者先完成。

## 十四、从成功案例提炼可复用规则

适合写进 Skill 的，是反复出现且确实影响正确性的条件：

- 中英文分 cue，避免错误朗读。
- 同一项目渲染串行，避免共享目录冲突。
- 新系列先样片，已确认系列不重复询问同样问题。
- 源稿变化后更新运行时，防止旧视频误交付。
- 按用户指定期数交付，不擅自扩展范围。

不应该固化为普遍规则的，是某一次任务中的偶然细节，例如某个用户名、某个绝对目录、某批固定五个单词，或者所有课程都必须用同一幅图。

一个好 Skill 让后续任务少踩坑，而不是让每次任务都重复执行不必要的程序。

## 十五、如何测试一个 Skill

本项目把验证分成三种。

### 结构检查

检查 SKILL.md 的前置信息、名称、引用及未完成占位内容。结构合法不代表工作流有效，但结构错误会直接影响发现和使用。

### 自动化测试

在仓库根目录执行：

```sh
node --test tests/workflow.test.mjs
```

现有七项测试覆盖正常交付、未审核稿、单元冲突、源稿过期、视频被修改、答题时机、音频证据、视觉门禁及参数范围等情况。测试中的模拟视频用于验证判断逻辑，不是证明渲染器能真实制作 MP4。

### 实际工程验证

已经使用 EP21–EP25 的真实成片验证技术交付工具，并在独立目录安装锁定依赖、通过 TypeScript 检查，使用既有 EP21 音频完成九场景、36 帧渲染检查。

这些结果证明了已测试范围内的工作流。它们不代表所有操作系统、全部音色或供应商状态都已经验证，也不代表每次更新都可以跳过检查。

对于触发行为，还应做人工场景演练：请求教材词汇续做时应选择本 Skill；请求数字人或横屏宣传片时不应强行套用；只请求文案时不应启动付费配音。本仓库没有声称已经实现全面的自动触发评测系统。

## 十六、分发到 GitHub 时保留什么

适合上传：Skill 指令、文档、最小模板源码、依赖锁、脱敏示例、辅助脚本和测试。

不应默认上传：TTS 密钥、`.env.local`、教材原件、个人路径、已生成音视频、第三方字体、未经确认授权的音乐和用户私有素材。

公开仓库只是公开了一套工具，不等于拥有所用教材、音乐和字体的再分发权。`.gitignore` 能减少误加文件，但不是完整的安全审查，也不能从已经提交的历史中抹去秘密。

修改仓库可见性、创建仓库或推送更新，都应有明确授权。写好两篇教程也不自动意味着已经推送到 GitHub，应区分本地文件完成与远程发布完成。

## 十七、后续如何维护和扩展

将仓库作为维护源，安装目录作为使用副本。修改规则后同步安装目录，重新验证；不要让两份 Skill 长期互相偏离。

小的内容修正优先改该期源稿，不要改全局模板。需要支持新年级、横屏、多说话人或其他 TTS 时，先明确数据与输出变化，再调整脚本、测试和样片，不能仅在说明里新增一句“已支持”。

如果将来增加自动发布功能，它应有单独的账号、内容和发布确认环节，不沿用“允许生成视频”作为“允许对外发布”的授权。

## 十八、总结：可复用来自清楚的边界

这套工作流可以概括为：

```text
用户范围与教材资料
    → 分期规划与内容审核
    → lesson 源稿与情境插画
    → 中英配音与真实时间线
    → Remotion 渲染
    → 技术检查、视觉检查与发音抽听
    → 视频、字幕及发布文案
    → 用户另行确认发布
```

Skill 的价值不是把每一步都自动按下去，而是让另一个会话、另一台电脑或另一个维护者知道：该读什么、该生成什么、哪些条件不能省略，以及何时才算真正完成。
